# 04 · Reliability closure: workouts, offline, background, GPS, camera, crash recovery (2026-11-17)

Branch `claude/legal-remediation` (worktree `remed`). Scope: workout persistence, offline sync, background behaviour,
GPS interruptions, camera permissions and crash recovery. Built on `docs/WORKOUT_LOGGING.md`,
`docs/audit-2026-11-14/workouts-programs-progress.md` and `nutrition-gps-health.md` (GPS), `docs/GPS_ACCURACY.md`,
`docs/GPS_BACKGROUND_IPHONE.md`, `docs/release/RC_2026-11-15.md` and `IPHONE_PLAN_2026-11-15.md`.

Everything below ran in this Linux container: Chromium at phone size (Playwright `mobile` project, Pixel 7) against a
production build, local Supabase with synthetic accounts, stand-ins for the AI provider and Open Food Facts.
**Nothing here ran on a phone.** "Offline" is Chromium network emulation, "killed" is a reload, clock changes are
Playwright's clock, and a refused camera is a `getUserMedia` that rejects. What only a device can show is in section 5.

## 1. Result in one paragraph

Most of the nine scenarios were already covered by unit, integration and browser tests. The gaps were in the browser
(finishing offline, a lost or refused Finish reply, two tabs, reload while offline, a refused camera), in clock
changes, and in damaged device copies. Closing them found **five defects, all fixed** with a test that failed before
the fix: Finish refused on every try after the phone's clock was put back (D1); sets logged after a clock change lost
to an older backup on reload (D2); a GPS recording frozen by one future-dated fix or a clock going back (D3); a
damaged device copy crashing the workout screen on every open (D4); and a two-tab race that wrote an older copy over
a completed set, on the device and on the account (D5, found by the new browser test failing intermittently). **29 new
tests** (22 unit, 7 browser); all pass. Results are in section 4.

## 6. Not changed, still open

- ~~**W-5**~~ **Fixed 2026-11-17 (02ca524)** on the owner's instruction: a Finish retry that reaches an already-saved
  workout and carries more completed sets replaces its contents as an edit (sets, volume, records; end time moved to
  the later Finish). A plain repeat, or an older copy with fewer sets, changes nothing. Tests:
  `tests/integration/finish-lost-reply.test.ts` (4; the two lost-reply cases failed before the fix) and the browser
  test "Finish saved but its reply lost, then another set logged". Edits to existing sets made after a lost reply
  *without* adding a set are not applied by the retry (the member can edit the workout in History).
- ~~No `src/app/global-error.tsx`~~ **Added 2026-11-17 (8a78793)**, with `tests/unit/global-error.test.tsx` (5). It
  cannot be triggered in a browser or device test without a deliberate crash hook, which was not added.
- **GPS splits after a clock jump (found by the 2026-11-17 code review, fixed in e9320b0):** D3's new line after a
  clock jump gave the next split a negative time, and the server refused the whole run. Split times now never go
  backwards; the test "a run whose clock went back can still be saved" failed (−265 s) before the fix.
- After a clock change: rest countdown inflated; a GPS recording whose clock goes back past its start has wrong times;
  cross-device "newest copy" follows each device's clock (section 3, i). Device tests DV-16.
- Two tabs editing at the same moment remain last-writer-wins; D5 only stops an *older* copy from overwriting a newer
  one.
