# QA report, 2026-11-05

The owner asked for eight checks (GPS end-to-end tests, GPS in production mode, the unit and hydration suites, an
updated tappable demo, an audit of the main areas, broken or unfinished things, demo isolation, and a prioritized
blocker list), then added: **"this should be for all iPhones … and Android models."**

**This is not a production-readiness sign-off.** Everything below ran on a local production build against a local
database, in a browser that emulates phones. No real phone, no hosted deployment, no real payment and no live AI model
was involved. Where something was not run, the report says so.

## How it was tested

- **App build:** `next build` with `DEMO_MODE` unset (a production build), served by `next start`, against the local
  Supabase stack in Docker (`npx supabase start`). Branch `claude/faith-discipleship`; the commit is in section 10.
- **Test configuration (browser tests):** the AI provider and Open Food Facts replaced by local mock servers
  (`ANTHROPIC_BASE_URL`/`OFF_API_BASE_URL` pointing at `E2E_ANTHROPIC_MOCK_PORT`/`E2E_OFF_MOCK_PORT`), so no paid
  call was made; `AUTH_RATE_LIMIT_SCALE=50` because the suite signs up many accounts from one address (the app's
  sign-up limit is 5 per 10 minutes per address, which is what failed the five GPS tests before).
- **Browser:** Playwright 1.64.1, Chromium 1194. WebKit (Safari's engine) is not installed in this environment; it ran
  on GitHub Actions: the iOS workflow's opening and navigation tests, and the device matrix for every iPhone size
  (section 9).

What this is and isn't: **Chromium emulation of each model's screen size, user agent and touch**, not the phones
themselves and not Safari's engine. It catches layout, sideways scrolling, overlap with the tab bar, script errors
and model-specific crashes; it cannot catch WebKit-only rendering differences, real keyboard behaviour, notches and
Dynamic Island cut-outs beyond the safe-area insets, or performance on old hardware. The iOS workflow on CI runs the
opening and navigation in WebKit at iPhone 15 size; everything else in WebKit and on real devices is in section 8 (F2,
F3).

The photos (8 screens per run) were reviewed for the narrowest phones (iPhone SE 320 pt, Galaxy S9+ 320 pt, Pixel 4
353 pt, Galaxy S5 360 pt) and the widest (16/17 Pro Max 440 pt, Pixel 9 Pro XL 448 pt, Galaxy A55 480 pt, unfolded
Fold 928 pt): titles truncate with an ellipsis rather than overflow, the five-tab bar fits, nothing is cut off, and the
unfolded Fold switches to the side-menu layout.

**WebKit (Safari's engine) for every iPhone size:** a new manual CI job (`webkit-iphones` in
`.github/workflows/ios.yml`, "Run workflow" with job = webkit-matrix) runs this same matrix for the 18 iPhone
viewports (39 models) in WebKit on a Linux runner.

- **First run** (`38fcb8b`, https://github.com/Joshfit77/Testing-testing-testing/actions/runs/42090521367): **0 of 18
  passed.** Three causes, read from its log:
  1. **A real defect, on every viewport:** React hydration error #418 on /profile (the time-zone list, section 6).
     Chromium never showed it because Chromium's zone list happens to match the server's closely enough.
  2. **Not an app defect:** WebKit reports each route prefetch the app cancels when the member leaves a page
     ("…/faith?_rsc=… due to access control checks") as a script error; Chromium doesn't. The check now counts these
     (same-host `?_rsc=` requests only) instead of failing on them; any other message still fails the run.
  3. **Test timing, on 3 viewports:** the first visit after onboarding was interrupted by the app's own welcome
     redirect, which WebKit finished late. The check now retries such a visit once and records it; an app that kept
     navigating on its own would still fail on the second attempt.
- **Second run** (`c1e5482`, with the fix and the two check changes,
  https://github.com/Joshfit77/Testing-testing-testing/actions/runs/42102774888): **18 of 18 passed** (13.1 min). The
  per-viewport counts of ignored prefetch messages and retried visits are in that run's artifact (`webkit-iphones`);
  I could not open it from this environment (its storage host is blocked by the environment's network policy), so
  those counts are not in this report.
- **Chromium phone matrix re-run on the same build** (`c1e5482`): **39 of 39 runs passed (74 models), 2,964 screen
  loads, 0 problems, 0 retried visits** (20.8 min). The tablet runs were not repeated on this build (6 of 6 on
  `cccdc3a`; the only app change since is the time-zone list).

This is WebKit on Linux, not Safari on an iPhone: it shares Safari's rendering and script engine but not iOS's
keyboard, safe areas on real hardware, or performance. Real devices are F2.
